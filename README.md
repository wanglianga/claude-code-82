# 🏊 蓝鲸社区泳池 · 预约入场与水质救生巡查协同平台

一个围绕「同一场次」把**居民端与现场端**拉到同一份实时事实上的一体化页面：居民预约 → 前台核验 → 救生巡查/水质监测 → 保洁维修工单 → 运营指挥/闭池联动，六类角色通过 TanStack Query 4 秒轮询共享状态，闭池时退费、补偿券、水质复测、救生清场与居民通知一次性联动，杜绝两端状态不一致。

技术栈：**React 18 + TypeScript + TanStack Query + Vite**（前端），**Express + TypeScript**（后端/静态托管），JSON 原子落盘（无需外部数据库，零依赖一键启动），多阶段 Docker 镜像、非 root 运行、内置 HEALTHCHECK。

---

## 原始需求

> 设计社区泳池预约入场与水质救生巡查页面，可使用 React、TypeScript 和 TanStack Query。居民预约泳道或亲子时段时，页面记录会员身份、年龄、健康承诺、是否带儿童、游泳水平和入场时段。前台核验预约、健康码或体检证明、儿童陪同人和储物柜，救生员端看到当前泳道人数、儿童区人数、深水区权限、水温、余氯、浊度和设备状态。运营人员巡查时，需要记录救生员站位、泳客违规跳水、儿童离开陪同人、地面湿滑、淋浴区拥堵和水质检测。若水质异常、雷雨临近、泳客抽筋、儿童走失、储物柜纠纷或预约超额，页面要让前台、救生员、保洁、维修和社区运营围绕同一场次处理。闭池或恢复开放时，预约退费、补偿券、水质复测、救生巡查和居民通知一起更新，避免居民端和现场端状态不一致。页面还要覆盖会员储值、教练课、团体预约、泳池消毒、救生员换岗和居民投诉。不同泳区的容量、风险和开放规则不同，运营人员要能看到一个场次从预约、入场、巡查到清场的完整状态。泳池还要处理外来访客、游泳培训机构包场、老人晨泳和暑期儿童高峰，运营人员需要在同一页面上看到商业预约和居民公益时段之间的冲突。

## 一键启动（Docker Compose）

```bash
cp .env.example .env        # 可按需修改 CC_PUBLISH_PORT（宿主发布端口，默认 3082）
docker compose up -d --build
```

- 容器内服务监听 `4000`，**仅应用端口发布到宿主**：`${CC_PUBLISH_PORT}:4000`；无数据库/缓存端口暴露。
- 数据保存在命名卷 `pool-data`（`/data/pool-db.json`，原子写）。首次启动自动播种当日演示数据（场次时间相对当前时刻生成，打开即有一个「进行中」的场次）。
- 取实际映射端口并访问（不要硬编码 3000/3082，避免并行任务冲突）：

```bash
docker compose port app 4000          # 例如 0.0.0.0:3082
# 浏览器打开 http://host.docker.internal:<端口>/
curl http://host.docker.internal:<端口>/api/health   # {"status":"healthy",...}
```

健康检查：镜像内置 `HEALTHCHECK`（wget 探活 `/api/health`），`docker compose ps` 可见 `(healthy)`。

停止并释放资源：

```bash
docker compose down          # 保留数据卷
docker compose down -v       # 同时清空演示数据（下次启动重新播种）
```

### 本地开发（可选）

```bash
npm install
npm run dev:server    # 终端 1：Express API :4000
npm run dev:client    # 终端 2：Vite :5173（/api 代理到 4000）
npm run build          # 类型检查 + 前后端产物
```

## 验证方式（宿主 docker compose up）

1. `docker compose up -d --build` 后 `docker compose ps` 为 `(healthy)`，`/api/health` 返回 healthy，首页与静态资源 HTTP 200。
2. 仓库附 `e2e-check.mjs`、`privacy-check.mjs`、`multi-closure-check.mjs`（不打进镜像），在宿主/容器网络可访问处执行（默认打 `http://host.docker.internal:3082/api`，可用 `TARGET=` 覆盖；每个脚本需在全新播种数据上单独运行：`docker compose down -v && docker compose up -d` 后等待 healthy）：
   - `node e2e-check.mjs`：**39 项业务断言**，覆盖
   - 六角色登录；亲子预约扣款；未签健康承诺/无深水证被拒；
   - 前台核验放行、储物柜重复分配与非绿码拒绝；
   - 异常水质（余氯 0.15、浊度 1.8）→ 自动限流、五角色事件立案、保洁/维修工单、限流期间停止入场；
   - 巡查（违规跳水→救生、地面湿滑→保洁工单）；
   - 抽筋事件跨角色 RBAC（保洁不能勾救生员任务、任务未清完不能关单）；
   - 闭池联动：原路退费到钱包、按笔发补偿券、预约状态变更、逐人居民通知、救生撤哨、复测/清场工单；
   - **恢复开放门禁**：无闭池后达标复测拒绝开池 → 维修复测达标 → 恢复 → 居民端同步看到通告；
   - 公益场商业包场冲突、超容量包场冲突、团体超额自动立案「预约超额」。
   - `node multi-closure-check.mjs`：**36 项多轮闭池断言**，覆盖不可变闭池档案（见下节）。
3. 手工体验建议路径：`li` 预约当前场次亲子时段 → `frontdesk` 核验放行（自动分配储物柜）→ `lifeguard` 用「异常样例」录入水质 → 各角色铃铛收到紧急通告并在「事件协同」完成本岗任务 → `maintenance` 完成消毒工单并复测 → `ops` 在「闭池与恢复」一键闭池（默认雷雨原因、退费+补偿+通知全勾选）→ 切到 `li` 看到余额与补偿券到账 → `maintenance` 复测达标 → `ops` 恢复开放；恢复后可再次闭池（如水质异常），在「闭池与恢复」底部查看多轮档案。

## 角色化数据视图（服务端脱敏，非前端筛选）

`GET /api/state` 不再下发全库快照，而是由 `server/views.ts` 依据**会话用户**在服务端裁剪，前端 TanStack Query 拿到的本身就是最小可见集合：

| 角色 | 可见范围 |
| --- | --- |
| 居民 | 仅**本人**预约、本人钱包流水、本人投诉、广播/个人通知；泳区只给人数/容量聚合；人员目录为空；锁区标题泛化（「该区域已被包场」，不见机构名与联系人）；课程学员名单只保留本人 id；撞锁区报错不回显机构名、他人预约码 |
| 前台 | 全部预约 + 有预约泳客的最小人员卡片（姓名/电话/会员等级/深水证，**无余额/补偿券**）；无钱包流水、无设备清单 |
| 救生员 | 看板聚合（各泳区在池人数、儿童数、深水证持有数、占用率）、水质、设备、排班、巡查、事件；无逐笔预约、无钱包、人员目录仅救生员且无电话 |
| 保洁 | 仅保洁岗工单、分派给保洁的巡查、需要保洁参与的事件；无预约/钱包/设备/投诉 |
| 维修 | 仅维修岗工单（含消毒复测）、设备、水质、需要维修参与的事件；无预约/钱包/投诉 |
| 运营 | 全量业务视图（退费处置、投诉答复、冲突协调所必需），人员卡片同样不含密码 |

闭池联动后，受影响居民各自只能在自己的快照里看到**自己那笔**退费流水、补偿状态与逐人通知；`privacy-check.mjs` 对上述边界做了 **43 项断言**（含快照 JSON 中不得出现他人手机号/姓名/预约码/陪同人等字符串级检查）。

## 闭池处置档案（不可变快照，支持同场次多次闭池）

每次执行闭池都会生成一条独立的 `ClosureRecord`（`server/domain.ts`），**一经固化不再被当前场次状态覆盖**：

- 档案逐字保存：闭池序号（第 N 轮）、原因分类与原文（雷雨/水质…）、闭池时间与操作人、是否要求复测、逐笔受影响预约的退费/补偿券/通知送达结果、退费总额、撤哨人数、消毒复测与清场工单、关联事件；
- 退费钱包流水、补偿预约、逐人通知与工单均带 `closureId`，反向引用同一档案；居民通知标题带「第 N 轮」；
- **恢复开放只更新当前开放状态**（`poolStatus`、清空 `activeClosureId`），并仅回写本轮档案的 `reopenedAt/reopenedBy/retestReadingId`；历史档案的原因与处置结果保持不变；
- 场次恢复后允许再次闭池：场次 `closureIds` 累积全部档案，运营时间线与「闭池与恢复」底部按轮次展示，雷雨档案与水质档案互不覆盖；
- 恢复门禁按**当前生效档案**校验（水质原因闭池必须有晚于该轮闭池时间的达标复测）；
- 角色视图同步裁剪：运营看全量档案与逐人明细，居民只看到含本人的条目，救生/保洁/维修只见原因、状态与本岗工单，不见逐人退款金额。


## 需求覆盖对照

| 需求点 | 实现位置 |
| --- | --- |
| 会员身份/年龄/健康承诺/带儿童/游泳水平/入场时段 | 居民「预约入场」表单（`src/pages/resident.tsx`），后端强校验健康承诺与年龄陪同规则 |
| 前台核验预约、健康码/体检证明、儿童陪同人、储物柜 | 「入场核验台」：非绿码/无证/重复柜号/容量超限/闭池限流一律拒绝并给出原因 |
| 泳道人数、儿童区人数、深水区权限、水温/余氯/浊度、设备状态 | 救生员「实时看板」：四泳区占用条、在场儿童、深水证持证比例、四项水质仪表、设备牌 |
| 救生员站位、违规跳水、儿童脱陪、地面湿滑、淋浴拥堵、水质检测 | 「救生巡查」六类问题 + 自动分派（湿滑/拥堵→保洁工单，水质→维修消毒工单）；「站位与换岗」记录上哨/接班 |
| 六种紧急情况围绕同场次协同 | 事件模板（`server/domain.ts`）按类型生成前台/救生/保洁/维修/运营各自处置清单，同屏进展时间线；保洁/维修事项自动转工单 |
| 闭池/恢复：退费+补偿券+复测+救生巡查+通知一起更新 | `changePoolStatus` 单次原子事务；恢复前强制存在「晚于闭池时间的达标复测」 |
| 会员储值/教练课/团体/消毒/换岗/投诉 | 钱包充值与流水、教学道课程报名扣款、≥5 人团体、消毒工单、换岗交接、投诉答复闭环 |
| 泳区容量/风险/开放规则差异 | 4 个泳区独立容量与规则（深水区高风险凭证、亲子区一对一陪同、浅水区老人优先），锁区名额参与容量计算 |
| 场次 预约→入场→巡查→清场 完整状态 | 运营「场次指挥台」：生命周期步骤条 + 汇总指标 + 全量时间线 |
| 访客/机构包场/老人晨泳/暑期高峰 | 七类预约 `BookingKind`，访客票价、公益免费、晚高峰容量预警 |
| 商业预约 vs 居民公益冲突 | 「商业/公益冲突」页：公益场商业包场、与既有居民预约、锁区重叠、超容量四类冲突自动标红，可解除锁区释放名额 |

## 目录结构

```
shared/            前后端共享：领域模型 types.ts、水质标准/计价 logic.ts
server/            Express API：store（原子 JSON）、seed（演示数据）、domain（业务编排/闭池档案）、views（角色化脱敏视图）、index（路由/RBAC）
src/               React：api(TanStack Query)、ui 组件、六角色 pages、components（事件/通告/通用）
Dockerfile         三阶段（deps→build→runner），非 root 用户 app，HEALTHCHECK
docker-compose.yml 单 app 服务 + 命名卷，仅发布 CC_PUBLISH_PORT
.env.example       端口/项目名等环境变量示例
e2e-check.mjs              39 项端到端业务断言（不打进镜像）
privacy-check.mjs          43 项跨角色数据泄露断言
multi-closure-check.mjs    36 项多轮闭池档案不可变断言
```

## 主要 HTTP 接口（均在 `/api` 下，Bearer Token）

`POST /auth/login` · `GET /state`（全量实时状态，前端轮询） · `POST /bookings` · `POST /bookings/:id/checkin` · `POST /water` · `POST /issues` · `POST /incidents` 及 `/action`、`/tasks/:tid/done`、`/resolve` · `POST /pool-status`（限流/闭池/恢复联动） · `POST /tasks`、`/tasks/:id/claim|done` · `POST /guards`、`/guards/:id/relief` · `POST /locks`、`DELETE /locks/:id` · `POST /wallet/recharge` · `POST /lessons/:id/enroll` · `POST /complaints` 等。
